# はじめに

自分はここ2、3年ほどテックカンファレンスや勉強会から離れていましたが、先輩に声をかけていただき[Kaigi on Rails 2026](https://kaigionrails.org/2026/) に参加してきました。

実務に活かせる知見が多く得られましたし、久しぶりにお会いする方々と話せて楽しかったです。何より「みんな転換点の中で悩んでいるんだ」と知れて勇気をもらえたので、参加して本当によかったと思っています。忘れないうちに、考えたことや感想をブログに残しておきます。

# 感想

## DHH のキーノート

- [Keynote: Where the tracks go next (DHH)](https://kaigionrails.org/2026/talks/dhh/)

DHH のキーノートでは、主に以下のような内容が語られていました。

- 私たちは今、大きな転換点にいる
- Ruby/Rails は他の言語に比べて少ない記述量で書けるため、開発速度が速い
- ただし、人間がコードを読んでいる限り、開発速度はいずれ頭打ちになる
- Rails のレールを通すよりも、素の Ruby で書いた方がパフォーマンスが良い場面もある
- これからの時代、アーキテクチャは一度決めたら変わらないものではなく、流動的になっていくものではないか？

発表を聞いた直後はあまり咀嚼できていませんでしたが、自分なりに以下のように解釈しました。

- 人間がコードを直接書いたり読んだりしなくなったとしても、Rails のような抽象度が高いフレームワークの価値はなくならないはず
- アプリケーションにとって重要なドメインやビジネスのロジックは、やはり人間が理解しておく必要がある
- そこで、人間が全体を抽象的に把握するのを助けるフレームワークが必要になる
- その一方で、パフォーマンスが求められるシビアな箇所はピュアな Ruby を使うなど、柔軟に使い分ける
- このようにして、アーキテクチャ自体が柔軟かつ流動的になっていく時代になるのではないか

## 大きな転換点の中で誰もが悩んでいる

- [Keynote (Matz)](https://kaigionrails.org/2026/talks/matz/)
- [Web Framework Benchmark Battle 2026, Any% (a_matsuda)](https://kaigionrails.org/2026/talks/amatsuda/)

Matz さんや a_matsuda さんのセッションからも、答えがわからない中でも「自分にできることをやっていくんだ」という姿勢を強く感じました。

また、懇親会で他の方々と話していても、誰もが大なり小なり AI の登場に戸惑いながら、手探りで自分にできることを模索していました。
かくいう自分も、AI の登場でエンジニアに求められる役割が変わり、日々の仕事の進め方に悩むことが多々あります。
だからこそ、「みんな同じように悩んでいるんだ」と知れたことは、自分にとって大きな勇気になりました。

変化が激しくて大変な時期ですが、まずは自分にできることをやっていこうという気持ちになりました。

## Rails の基本にして奥義は、やはりモデリングではないか

- [Domain Modeling with Vanilla Rails: 「操作」から再考するRailsの設計論 (yasaichi)](https://kaigionrails.org/2026/talks/yasaichi/)
- [Event is what happens (moro)](https://kaigionrails.org/2026/talks/moro/)

yasaichi さんのセッションでは、Rails の生産性の高さは以下の3つが綺麗に 1対1 になっている点にある、という整理がされていました。

- URL
- Controller の action
- Model

一方で、この構造では Model が複数のユーザー操作にまつわるロジックを抱え込みがちになります。そこで、Controller と Model の間にもう1つ層を設け、操作を概念化したクラスを切り出すアプローチが提案されていました。

また moro さんのセッションでは、設計上「イベントエンティティ」を見出す重要性が語られていました。そして実装時には `Rails.event` を使い、イベントに起因する後続処理を Subscriber として実装することで、Publish 側が後続処理を気にせずに済み、疎結合な状態を実現できるとのことでした。

この2つのセッションを聞いて、自分は「Rails の基本にして奥義はモデリングなのだ」と改めて感じました。
モデリングが出発点なので、そこに「操作」や「イベント」が見出せていないと、リソース系のモデルにすべてを押し込むことになり、設計に無理が生じます。土台となるモデリングがしっかりしていれば、責務の切り出しも考えやすくなります。

最近、仕事では業務フローの整理や PRD 作成など、コードを書く前の工程を担当することが増えています。要件定義の段階から「業務上必要な概念の見出し」を丁寧に行いたいと、気持ちが引き締まりました。

## その他印象に残ったセッション

### 真の REST 2026

- [真のREST 2026 (t_kawa)](https://kaigionrails.org/2026/talks/tkawa/)

Sendagaya.rb でお世話になっていた t_kawa さんの発表でした。

- Web の成功要因は、拡張性（古いものを壊さずに新しいものを足せること）と、インターネット規模（信頼できない相手と通信しても壊れないこと）にある
- REST はそれを実現するための設計原則
- そして今、AI エージェントという「信頼できない相手（汎用クライアント）」が新たに登場した
- では、今の時代に適したレスポンス表現とは何か？
- 実験の結果、有効だったのはハイパーメディアを返すことだった
- これはまさに、元々の REST な Web の構造そのものではないか
- つまり、REST の制約は現代においても何も変わらず有効である

という内容だったと受け止めています。
発表直後は自分の中でこの流れをうまく消化できていませんでしたが、セッション後に t_kawa さんとお話ししたことで一気に線として繋がりました。四半世紀前に確立された理論が、AI 時代の今になってもそのまま通用するのは、非常に面白いと感じました。

### スマートバンク社の方々の発表

- [作れる、でも消せるか？──安全に「枯らして消す」機能削除術 (ksbmyk)](https://kaigionrails.org/2026/talks/ksbmyk/)
- [Railsで挑む大量データ永続化 〜600億件を永続化するための設計とボトルネックとの戦い〜 (sho-work)](https://kaigionrails.org/2026/talks/sho-work/)

お二方の発表を聞いて、「日々の仕事に非常に丁寧に向き合っている」という印象を受けました。
ここでいう丁寧とは、その時々の状況や課題をしっかり整理して、一つひとつ必要な合意形成や判断をしながら、確実に前に進めていく姿勢のことです。
こうした地道で丁寧な進め方を大事にしている姿を見て、自分も日頃の仕事への姿勢が正される思いがしました。
